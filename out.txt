二、接口语义
【alertcenter.py】
- init(db)
  CREATE TABLE IF NOT EXISTS alert_rules(...) 与 alerts(...)，DDL 与契约逐字一致（match_kind 限
  keyword/source/sentiment；level 限 info/warn/critical；status 限 open/acked/closed）。幂等，可重复调用。
- evaluate(db, moment=None)
  遍历 enabled=1 的规则（按 id 升序）：按 match_kind 在 window_minutes 窗口内统计命中 records 数——
  keyword = records.title 或 records.summary 字面量包含（转义 LIKE 的 % / _，按字面量匹配）；
  source  = feeds.name 等于 match_value（records JOIN feeds）；sentiment = records.sentiment 等于 match_value。
  时间窗口口径与 storage.overview_stats 一致：coalesce(published_at, fetched_at) >= moment - window。
  命中数 >= threshold 且同规则不在冷却期（最近一条告警 last_seen + cooldown_minutes > moment）时新建一条告警：
  id = "alert-" + storage.digest(json_bytes([rule_id, moment, match_kind, match_value, hit_count, id 样本]))；
  metrics = JSON{hit_count, threshold, window_minutes, match_kind, match_value}；
  evidence = JSON 数组，命中 record id 前 20 条；first_seen = last_seen = moment；status = open。
  返回 {"created": 本轮新建条数, "checked_rules": 检查的启用规则数, "evaluated_at": moment,
  "triggered": [{alert_id, rule_id, name, level, hit_count}...]}。
  同一 moment 重复调用时 INSERT OR IGNORE 幂等，created 只计真实插入的行。
- create_rule(db, payload)
  校验后插入并返回新规则 dict。只接受 name/match_kind/match_value/window_minutes/threshold/level/
  cooldown_minutes 七个字段（多余字段 400）。name 1–100 字符（空白折叠）；match_kind 必填且属于三值；
  match_value 1–200 字符；window_minutes 默认 60（1–10080）；threshold 默认 1（1–100000）；
  level 默认 info；cooldown_minutes 默认 30（0–10080）；created_at 为 UTC；enabled 固定 1。
- rules(db)：全部规则（含 enabled=0），按 id 升序的 dict 列表。
- alerts(db, limit=100)：告警 dict 列表，按插入顺序倒序（rowid）；limit 必须 1–500；metrics/evidence
  在返回时解析为 JSON 对象（解析失败则保留原字符串）。
- ack(db, alert_id)：把 status 由 open 改为 acked，last_seen 不变（UPDATE 只写 status）；返回更新后的告警。
  alert_id 不存在 → ValueError("告警不存在")；非 open → ValueError("仅未确认（open）的告警可确认")。
- start_scheduler(db_path, interval_seconds=60)
  起一个 daemon 线程，每 interval_seconds 秒用 storage.connect(db_path) 打开库，init(db) 后跑一次
  evaluate(db)；循环内任何异常只写 stderr（前缀 [alertcenter] scheduler evaluate failed），不抛出、不终止循环。
  幂等：已启动则直接返回 False，不重复起线程（SCHEDULER 标志受 SCHEDULER_LOCK 保护）。
  首次执行发生在第一个间隔到点之后（先 sleep 再 evaluate）。

【server.py 路由】沿用现有 Origin/Host 校验与错误风格（ValueError→400，OSError/sqlite3.Error→500）
- GET  /api/alert-rules        → 200，alertcenter.rules(db)
- POST /api/alert-rules        → 201，alertcenter.create_rule(db, body)；body 见上
- GET  /api/alerts?limit=100   → 200，alertcenter.alerts(db, limit)；limit 必须为 1..500 的单个整数
- POST /api/alerts/<id>/ack    → 200，alertcenter.ack(db, id)
- POST /api/alerts/run         → 200，alertcenter.evaluate(db)（立即跑一次并返回统计）
- GET  /alert-panel.js         → 200，静态脚本（text/javascript; charset=utf-8）
- 启动期：connect() 内 analysis.init(db) 旁新增 alertcenter.init(db)（每次连接/启动都保证表存在）；
  __main__ 启动块在 storage.recover_runs/analysis.recover 之后调用 alertcenter.start_scheduler(DB)。
  说明：所有 POST 与既有实现一致，必须先通过 Origin/Host 校验，且请求体必须是 JSON 对象（无字段时发 {}），
  否则按既有风格返回 400“请求内容为空或超过限制”。

【alert-panel.js / index.html / style.css】
- index.html 在 view-watch 视图内加入 <section class="panel" id="alert-center-panel"><div id="alert-center" hidden></div></section>，

  级别单元格用 alert-level / alert-level-<level> 类。
- style.css 仅末尾追加：.alert-open/.alert-acked/.alert-closed/.alert-level/.alert-level-info|warn|critical。
